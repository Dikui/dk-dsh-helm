# Teamwork · 先冻结规格，再让多角色协作

Teamwork 面向需要多轮验证的工程任务。Host 保存目标、规格版本、问题账本和验收记录，不靠某一位模型“记得”旧问题。它是独立的 DSH 插件，不依赖 Swarm 或 Boost。

## 第一次运行

在测试 profile 的插件管理页添加本目录或安装包，从允许本地子代理、原生工具和持久存储的**根会话**开始。先切到可丢弃的工程副本。安装包面向 DSH `0.2.2-rc.5`。在输入框发送如下多行命令（去掉代码围栏），例中的测试命令必须已在你的工程中存在：

```text
/teamwork skip --mode swe-light 修复负数价格被接受的问题；不要改现有验收测试。
@check npm test
```

1. 读草稿：检查目录、任务、拒绝的实现方式、验收命令。`skip` 只跳过访谈，**不跳过确认**。不使用 `skip` 时按命令返回的访谈问题补充约束。
2. 在**同一根会话**亲自发送草稿给出的整条确认命令，不要照抄文档里的占位符。只有这一步后才能派工。`@check` 是你授权 Host 运行的前台命令；它可以被多轮验证重复执行，应能安全重跑，不要填写部署、发布或有不可逆副作用的命令。
3. 用 `/teamwork status` 看当前阶段；用 `/teamwork dossier` 读取可交接的 Markdown 摘要，包含原始请求、规格版本、任务、未决问题和最近的检查回执。`/teamwork pause`、`/teamwork resume` 和 `/teamwork cancel` 分别对应暂停、人工恢复及终止；这些操作不会撤销已完成的文件修改。

## 路线与边界

- `swe-light`：一个明确的小改动，执行和复核串行；旧问题不能仅因后续报告没提及就算关闭。
- `general`：用于需要调查和多个验证视角的工作。执行角色、只读验证角色与终局审计使用各自的子会话。用户的检查与模型的结论是两类证据；命令未成功、问题仍未关闭或完整性被否决都不应报告胜利。
- 各角色继承当前组合许可与资源上限；请先在测试工程试运行。执行者可改工程文件，工具策略和工作区约定**不是操作系统沙箱**；重要的验收脚本应置于其不能修改的地方。不建议在正在工作的主工作区试跑，多个协作插件之间也没有统一的文件写锁。
- Campaign 状态通过 Host 的 `storageDomain` 写入，不把协作日志散落在业务仓库。无需自建定时向用户会话发消息的 cron，也不会因为界面刷新而批准规格。
- 本包是工程路线首版，不是完整替代品：不包含科研、文档锦标赛、Lean 证明 DAG、常驻 Sentinel 定时接棒或 40+ 角色库。Host 重启后已开始的运行暂停，需手动 `resume`；不会复活旧模型进程、清理工作树或安全隔离不可信代码。

## 验证

安装依赖后运行 `npm test`。可选真实存储测试接受 `DSH_TEST_RUNTIME`（本机 DSH 安装中的包解析清单）；在 Desktop ASAR 内需用 `ELECTRON_RUN_AS_NODE=1` 配合该 Desktop 的可执行文件运行测试。该测试只在临时目录建立新 Backend，不访问日常 profile。
